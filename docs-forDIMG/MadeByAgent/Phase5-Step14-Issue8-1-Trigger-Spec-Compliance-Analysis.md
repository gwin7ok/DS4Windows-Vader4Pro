## 1. gwin7ok氏が整理した仕様（原文要約・5項目）

| # | 仕様項目 |
|---|---|
| ① | トリガーとして設定された全ボタンが押された時点でトリガー成立とみなしSpecialActionを実行する。実行完了までは、再度トリガーが成立しても新たな実行は行わない。 |
| ② | トリガー成立の始点は「トリガー設定された全ボタンのうち最後に押されたボタンが押された瞬間」。終点は「トリガー設定されたボタンのうちどれか1つでも離された瞬間」。 |
| ③ | （②の具体例）L2→PSの順に押すとPS押下時が成立、PS解放時が解除。この時点でL2はまだ押されていても、再度PSを押せば2回目の成立となるが、1回目のSpecialAction実行が完了していないなら2回目の実行は阻止されるべき。 |
| ④ | プロファイル適用後（プロファイル切替・コントローラー接続・プロファイル保存等）は、それ以後に発生したトリガー成立イベントのみを成立とみなす。プロファイル適用直後に全ボタンが既に押された状態にあっても、それだけでは成立とみなさない。**gwin7ok氏はこの項目の違反がバグの発生源である可能性を自ら指摘している。** |

## 2. 現行コードの実地追跡結果（項目別）

### 2.1 ①・②（成立の始点＝全ボタンANDのエッジ、終点＝いずれか1つの解放）→ **仕様通り実装されている**

`Mapping.cs` の `MapCustomAction` 内、SpecialActionのトリガー判定は以下の構造になっている（4930行目以降、`triggeractivated`の算出ブロック）。

```csharp
// 5038-5046行目付近（既定の判定分岐）
for (int i = 0, arlen = action.trigger.Count; i < arlen; i++)
{
    DS4Controls dc = action.trigger[i];
    if (!getBoolSpecialActionMapping(device, dc, cState, eState, tp, fieldMapping))
    {
        triggeractivated = false;
        break;
    }
}
```

これは「トリガーに設定された全ボタンが現在押されているか」を**毎回のマッピング評価サイクルで再計算する水準（レベル）判定**である。「成立の瞬間＝最後のボタンが押された瞬間」は、この水準判定の結果を１つ前のサイクルの状態（`ActionManager.IsBeingTriggered`、後述）と比較し、`false→true`に変化した回だけを「新規成立」として扱う仕組みで実現されている（5079-5136行目、`if (triggeractivated) { ... if (!GetBeingTriggered(...)) { 実行 } }`）。全ボタンが押されるまでは水準判定は`false`のままであり、最後の1つが押された瞬間に初めて`true`に切り替わるため、**数学的に「最後に押されたボタンが押された瞬間」と同一の意味になる**。この部分は仕様①・②の前半（成立の始点）と一致している。

成立の終点（②後半）についても、`else`側分岐（5550-5651行目）で、水準判定が`false`（＝トリガーに設定された全ボタンのうち少なくとも1つが押されていない）になった場合に、`Profile`型を含む多くのアクション種別で`DispatchOrSetBeingTriggered(action, device, false)`が呼ばれ、`BeingTriggered`ラッチが即座に解除される実装になっている。これは「トリガー設定されたボタンのうちどれか1つでも離された時点で成立状態が終わる」という仕様と一致している。

**結論**: 仕様①・②（特にその前半：成立と解除のタイミング自体）は、現行コードで概ね正しく実装されている。

### 2.2 ③（実行完了までの再実行阻止）→ **明示的な仕組みは存在しない（現状は物理的な「離す」動作に依存した代替実装）**

現行コードで「再実行を阻止」しているのは、`BeingTriggered`ラッチが`true`のまま維持される間は`!GetBeingTriggered(...)`が`false`になり再実行がブロックされる、という仕組みのみである。これは「物理的にボタンが押されっぱなしである間は再実行しない」という意味では機能するが、**仕様③が求めている「SpecialActionの実行そのものが完了したかどうか」という基準ではない**。

`Profile`型SpecialActionの実行（`Global.ApplyProfile`）は現状同期的に呼ばれており、呼び出し元のマッピング処理スレッドはこの完了を待ってから次の入力評価に進む構造になっているため、**「実行中に同一トリガーが物理的に２回成立する」という状況は、少なくとも同一スレッド上では構造的に発生しにくい**（1回目の実行が終わるまで次の入力自体を評価できないため）。このため、③自体は今回報告された暴走ループの直接原因ではないと判断する。**【2026-09-12追記】この点はgwin7ok氏に確認いただいたところ、直接原因でなくとも明確な必須要件として今回のスコープに含めることが確定した。詳細な設計は§4を参照。**

### 2.3 ④（プロファイル適用後は"以後の"成立イベントのみを成立とみなす）→ **【違反を確認・これがバグの直接原因】**

`Global.ApplyProfile`（`ScpUtil.cs`）は、プロファイル適用のたびに以下を無条件に実行する。

```csharp
// ScpUtil.cs 3223-3241行目付近
try { DS4Windows.ActionManager.ClearAllEntries(); } catch { }
...
DS4Windows.Mapping.ClearKeyButtonControllersForDevice(device);
try { DS4Windows.ActionManager.ClearDeviceState(device); } catch { }
```

`ClearDeviceState(device)`の実体（DI経由で実際に使われる`DefaultActionManager.ClearDeviceState`、`DS4Windows/DS4Control/DefaultActionManager.cs` 193-225行目）は、当該デバイスの全SpecialActionについて、以下の1行で状態を無条件に**新品へ差し替える**。

```csharp
// DefaultActionManager.cs 209行目
ent.States[device] = new ActionInstanceState();
```

`ActionInstanceState`（`ActionManager.cs` 12-24行目）の`BeingTriggered`は、内部フィールド`_beingTriggered`の既定値`false`をそのまま返す設計であり、**「現在その物理トリガーが押されているかどうか」を一切考慮せずに常に`false`から再出発する**。

一方、トリガー成立の実行判定（`Mapping.cs` 5133行目、`Profile`型の場合）は次の通りである。

```csharp
if (!GetBeingTriggered(index, action, device) && (...))
{
    // ApplyProfile を実行
}
```

`GetBeingTriggered`は最終的に`ActionManager.IsBeingTriggered(action, device)`→`GetStateFor(action, device).BeingTriggered`を返すだけであり、上記の「プロファイル適用のたびに`false`へリセットされる」状態をそのまま参照する。**この2つを組み合わせると、プロファイル適用の瞬間に物理的にトリガーが押されたままであった場合、その押しっぱなし状態を「新規の立ち上がりエッジ」と誤認し、即座に次のSpecialActionを実行してしまう。**

これは仕様④が明示的に禁止している状況——「プロファイル適用直後に全ボタンが既に押された状態にあっても、それだけでは成立とみなさない」——にまさに違反しており、gwin7ok氏がご自身で指摘された通り、**これが本バグの直接の技術的原因である**と確定した。

#### 実機ログとの整合性
提供いただいた実機ログ（`ds4windows_log.txt`）では、`原神DS4□`→`ACO`→`原神DS4_for_gwin`→`原神DS4□`→…という3プロファイルが約1.0〜1.4秒間隔で自動的に巡回し続けており、各回の実行直前には必ず`SpecialAction PROFILE: beingTriggered=False`が記録されている。これは、各プロファイルの適用完了直後、ユーザーが物理トリガーをまだ離していない状態で`ClearDeviceState`によって`BeingTriggered`が`false`にリセットされ、その直後のマッピング評価サイクル（実測500Hz超）で押しっぱなし状態が「新規成立」と誤認され、新プロファイル側の同一トリガーに割り当てられた別のプロファイル切替アクションが即座に発火する、というサイクルが自己持続的に繰り返された結果と、技術的に完全に整合する。

### 2.4 ⑤（成立時、最後に押されたボタン自身の単体出力を抑制）→ **【追加調査済み】現行実装は「最後の1つ」ではなく「トリガー設定された全ボタン」を対象に、成立期間中ずっと抑制する仕様になっている**

`Mapping.cs` 5092-5096行目（`ResetToDefaultValue`呼び出し）を実装レベルで確認した。

```csharp
for (int i = 0, arlen = action.trigger.Count; i < arlen; i++)
{
    DS4Controls dc = action.trigger[i];
    ResetToDefaultValue(dc, MappedState, outputfieldMapping);
}
```

`ResetToDefaultValue`（7950-7973行目）は、指定された物理コントロールの**当該フレームの出力値**を、ボタンなら`false`、軸なら中央値(128)、トリガーなら`0`へ強制的に戻す処理である。この呼び出しは`triggeractivated`（トリガー全ボタン押下）が`true`である**限り、毎フレーム**実行される。

これを踏まえると、現行実装の実際の仕様は以下の通りである。

* トリガーに設定された**全ボタン**（例: L2とPSの両方）について、コンボ成立中は毎フレーム、そのフレームのデフォルト出力を強制的にリセットしている。「最後に押された1つのボタンだけ」を特定して抑制する、という区別は行っていない。
* ただし、これは結果として仕様⑤の具体例と**矛盾しない**部分がある。L2が単独で押されていた期間（PSがまだ押されていない間）は、この`SpecialAction`のトリガー判定ブロック自体に到達しない（`triggeractivated`が`false`のため）ので、L2は通常のマッピング処理を経て**普通に単体出力される**。L2の単体出力自体は、コンボが成立する前の時点で既に完了している。
* 一方、**PSが押された後（コンボ成立中）も、L2の出力は毎フレーム強制的に中立値へ戻され続ける**。ユーザーの記述「L2のデフォルトの信号出力…がなされる」を「コンボ成立前に一度なされていればよい」と読むか、「コンボ成立中も継続してなされるべき」と読むかで、現行実装が仕様に合致するかどうかの評価が変わる。

**確認をお願いしたい点**: 現行実装は「コンボ成立中は、参加している全ボタンの単体出力を一律に止める」という設計になっている。もしgwin7ok氏の意図が「コンボ成立中もL2側の出力は継続してほしい（PSだけを止めればよい）」というものであれば、これは仕様⑤との明確な差分であり是正が必要になる。逆に「コンボ成立中は全ボタンの単体出力を止めて構わない（既に出力済みの分があればそれで十分）」という理解であれば、現行実装のままで問題ない。**この点は実装差分の有無に直結するため、ご意図を確認したうえで対応要否を判断したい。**

なお、いずれの解釈であっても、**本項目は今回報告されたプロファイル連続切替の暴走バグ（Issue 8-1本体）の発生には関与していない**ことを確認済みである（暴走ループはトリガー成立可否の判定そのものに起因しており、成立後の出力抑制ロジックとは独立している）。是正が必要と判断された場合は、Issue 8-1本体の対応（§3）とは別のマイクロタスクとして切り出すことを推奨する。

### 2.5 補足説明: MultiAction型（Guide複合キー）の"連射"とは、具体的にどのような現象か

gwin7ok氏より「これがどういう現象を指しているのか理解できていない」とのご質問をいただいたため、平易に説明する。

#### 何が起きているか
ログの後半（5886行目以降）で、`0101_GI_マップ`という名前のSpecialAction（種別は`MultiAction`＝Guideボタン等と組み合わせたマクロ的な機能）が、**人間が実際にボタンを押し直した回数よりも明らかに多い回数、極めて短い間隔（同一ミリ秒内に何度も）で繰り返し実行されてしまっている**、という現象である。

イメージとしては、ボタンを1回押しただけなのに、コントローラーが「押した→離した→押した→離した…」を1秒間に何十回も勝手に繰り返し報告しているかのように、アプリ側がこのSpecialActionを何度も実行してしまっている状態である。

#### なぜIssue 8-1（プロファイル連続切替の暴走）と分けて考える必要があるのか
Issue 8-1本体（プロファイル切替の暴走）は、**「プロファイルを読み込み直すたびに、"押しっぱなし判定"の記憶がリセットされてしまう」**ことが原因であると特定できた（§2.3）。つまり「プロファイルの再読み込み」というイベントが引き金になっている。

一方、この`0101_GI_マップ`の連射は、**プロファイルの再読み込みを伴わない場面でも起きている**痕跡がある。これは、Issue 8-1本体とは**別の仕組みで動いているコード**（`triggeractivated`や`BeingTriggered`という「現在押されているかどうかの判定」の仕組みを使わず、「1つ前にコントローラーから受け取った信号と、今回受け取った信号を直接見比べる」という、また別の判定方法を使っているコード）で発生している。

具体的には、Guideボタン（PSボタン）が実際にはずっと押されっぱなしであるにもかかわらず、アプリ側が参照している「1つ前の信号」の記録の中で、なぜかGuideボタンの状態が正しく反映されていない（＝毎回「さっきは押されていなかった」という誤った記録になっている）可能性がある。もしそうだとすると、ボタンは物理的には離されていないのに、アプリからは「今まさに新しく押された」ように見え続けてしまい、押しているだけで際限なく実行され続けてしまう。

#### なぜ別問題として切り分けを提案しているか
Issue 8-1本体の是正（§3、プロファイル再読み込み時の誤判定を防ぐ対応）を行っても、この`0101_GI_マップ`のようなGuideボタン絡みの連射は、**発生の仕組みが異なるため解消しない可能性が高い**。そのため、これは「Issue 8-1のついでに直る」問題ではなく、Guideボタンの状態記録がなぜ正しく更新されないのか、を別途調査する必要がある、という位置づけで報告した。

**現時点ではこれは「おそらくこういう仕組みで起きているだろう」という技術的な仮説の段階であり、実際に原因を確定するには追加のログ調査またはコード調査が必要である。** gwin7ok氏のご判断を仰ぎたいのは、「このGuideボタン絡みの連射も、今回のIssue 8-1の作業の中で一緒に調べて直してしまうか」「それとも一旦切り離して、Issue 8-1の是正を先に済ませてから、別の課題として改めて調査するか」という進め方の点である。

## 3. 対応方針（設計案）

### 3.1 基本方針

仕様①・②（成立・解除のタイミング判定自体）は正しく実装されているため変更しない。**仕様④の違反のみをピンポイントで是正する。** 具体的には、「プロファイル適用によって`ActionInstanceState`が再生成された直後は、少なくとも1回、対象トリガーが『成立していない（＝ボタンが押されていない）』状態を観測するまでは、たとえ全ボタンが押された状態が検出されても新規成立とみなさない」というガードを追加する。

### 3.2 具体的な設計

1. `ActionInstanceState`（`ActionManager.cs`）に新しいフラグを追加する。

   ```csharp
   // プロファイル適用直後は true。以後、当該アクションのトリガーが
   // 一度でも「未成立（全ボタン押下でない）」状態として観測されるまでは、
   // たとえ全ボタン押下状態が検出されても新規成立とみなさない
   // （Issue8-1是正: 仕様④「プロファイル適用後は、以後発生した成立イベントのみを成立とみなす」）
   public bool RequiresFreshPressAfterReset = true;
   ```

2. `Mapping.cs`のトリガー判定箇所（`triggeractivated`確定直後、5079行目 `if (triggeractivated)` の手前）に、共通の「アーム」処理を追加する。

   ```csharp
   if (!triggeractivated)
   {
       // 未成立状態を観測 = 以後の成立イベントは正規のものとして扱ってよい
       var st = ActionManager.GetStateFor(action, device);
       if (st != null) st.RequiresFreshPressAfterReset = false;
   }
   ```

3. 成立時の実行判定（`Profile`/`Program`/`GyroCalibrate`等、`!GetBeingTriggered(...)`で実行可否を判定している全箇所）に、上記フラグのチェックを追加する。

   ```csharp
   var st = ActionManager.GetStateFor(action, device);
   bool blockedByFreshPressGuard = st != null && st.RequiresFreshPressAfterReset;
   if (!GetBeingTriggered(index, action, device) && !blockedByFreshPressGuard && (...))
   {
       // 実行
   }
   ```

4. `ActionInstanceState`の既定値は`RequiresFreshPressAfterReset = true`のままでよい。`ClearDeviceState`が`new ActionInstanceState()`で差し替えるたびに、自動的にこのフラグは`true`（＝要フレッシュプレス）に戻るため、プロファイル適用直後の防御が自然に効く。

### 3.3 この設計の妥当性

* **既存の正しい挙動（仕様①・②）を一切変更しない**: `triggeractivated`の算出ロジックにも、成立時・解除時の既存処理にも手を入れない。追加するのはあくまで「新規成立を許可するかどうか」の追加ゲートのみ。
* **仕様④の要求を過不足なく満たす**: プロファイル適用直後に全ボタンが押されたままであれば`RequiresFreshPressAfterReset`は`true`のままなので実行はブロックされ、その後ユーザーが実際に1つでもボタンを離した瞬間（`triggeractivated == false`を観測した瞬間）にフラグが解除され、以後は通常通り動作する。
* **全SpecialAction種別に横展開可能**: `ActionInstanceState`はアクション種別を問わない共通の状態オブジェクトであるため、`Profile`型に限らず`Program`型・`GyroCalibrate`型など、同じ`GetBeingTriggered`ゲートを使う全ての種別に対して同一の保護が自動的に及ぶ。
* **既存の250msデバウンス（`DefaultProfileSwitcher.cs`）と役割が重複しない**: 既存デバウンスは「短時間内の連続切替」を防ぐ時間ベースの保険であり、今回追加するガードは「プロファイル適用直後の押しっぱなし誤検知」を防ぐ状態ベースの是正である。両者は独立した防御層として併存させる。

### 3.4 リスクと確認事項

| リスク | 対応 |
|---|---|
| `RequiresFreshPressAfterReset`のチェック漏れ箇所が残ると、その種別だけ仕様④違反が temporarily 残存する | `GetBeingTriggered`を実行可否判定に使っている全箇所を`grep`で洗い出し、漏れなく追加する（Program型・GyroCalibrate型・Profile型を確認済み、他の型の要否も実装時に再確認する） |
| プロファイル適用**以外**の理由で`ClearDeviceState`が呼ばれるケース（コントローラー切断等）で、意図せずガードがかかり続ける可能性 | `ClearDeviceState`の全呼び出し元を洗い出し、それぞれのケースで「以後、一度もボタンを離さなくても正規動作させたい」特殊ケースがないかを確認する |

## 4. 新規要件: 同一SpecialActionの実行重複禁止（仕様③の厳格化・gwin7ok氏指示による追加スコープ）

### 4.1 要件の確定

gwin7ok氏より、§2.2で「本バグへの直接の寄与は薄い」と評価した仕様③について、以下の通り**明確な必須要件として今回の作業に含める**指示があった。

> 同じSpecialActionが実行中は、そのSpecialActionの実行が完了するまで、トリガーが新しく成立しても実行は阻止されるか、もしくは実行キューに入れて先に実行されたSpecialActionの完了後に実行される形にしたい。**実行期間が重なる（オーバーラップする）形は不可。**

別のSpecialAction同士が同時に実行されること自体は問題ない。**同一のSpecialAction（同一デバイス上）**について、実行期間が重複してはならない、という要件である。

### 4.2 現状調査: 類似の既存実装パターンの有無

`ActionInstanceState`（`ActionManager.cs`）には、既に`IsMacroRunning`という「今まさにこのマクロが実行中かどうか」を表すフラグが実装済みであり、`Mapping.cs`の`PlayMacroTask`（6080-6324行目）は、新しいマクロの反復を開始する前に必ずこのフラグを確認する「開始ガード」として使っている（例: 6080行目 `PlayMacro START GUARD`のログ）。**すなわち、"同一アクションの実行中は新規実行を始めない"という設計思想自体は、Macro型に限ってはコードベースに既に先例として存在する。**

一方、`Profile`型・`Program`型・`GyroCalibrate`型については、実行中かどうかを表す専用フラグが存在せず、実行可否の判定は`BeingTriggered`（＝物理的に押されているかどうかのラッチ）だけに依存している。`Profile`型の実行（`Global.ApplyProfile`）は現状同期呼び出しであるため、**単一デバイス・単一スレッド内での真の同時実行は構造上起きにくい**が、以下のようなケースでは理論上オーバーラップが起こり得るため、明示的なガードを設けることが妥当と判断する。

* 将来、`ApplyProfile`やマクロ以外のSpecialAction実行が非同期化された場合（例: プロファイル読込のバックグラウンド化、外部プロセス起動の非同期待機化）。
* 同一の`SpecialAction`定義（同名）が、リンクプロファイル等の仕組みにより複数デバイスから共有され、かつ将来的に「デバイス横断で同一実行を1つに制御したい」という要件が生じた場合（本書では対象外とし、当面は現行の設計方針＝`ActionInstanceState`はデバイスごとに独立、を踏襲する）。

### 4.3 設計案

1. `ActionInstanceState`に、`Profile`／`Program`／`GyroCalibrate`等（Macro以外）向けの汎用フラグを追加する。

   ```csharp
   // Issue8-1(2): 同一アクションの実行重複禁止用。Macro型はIsMacroRunningで既に管理されているため、
   // それ以外の種別（Profile/Program/GyroCalibrate等）向けに新設する。
   public bool IsExecuting = false;
   // 実行中に新たな成立イベントが発生した場合、完了後にもう一度だけ実行してほしいという要求を記録する
   // （実行キュー方式・キュー深さ1、無制限キューによる際限のない滞留を防ぐため）
   public bool PendingReExecutionRequested = false;
   ```

2. `Profile`型の実行箇所（`Mapping.cs` 5133行目周辺）を、実行の前後を`try/finally`で囲み、`IsExecuting`を管理する形に変更する。

   ```csharp
   var st = ActionManager.GetStateFor(action, device);
   if (!GetBeingTriggered(index, action, device) && !blockedByFreshPressGuard && (...))
   {
       if (st != null && st.IsExecuting)
       {
           // 実行中 → キューに積む（1件のみ。既にキュー済みなら何もしない）
           st.PendingReExecutionRequested = true;
       }
       else
       {
           if (st != null) st.IsExecuting = true;
           try
           {
               // 既存の実行処理（ApplyProfile 等）をそのまま呼び出す
               ...
           }
           finally
           {
               if (st != null)
               {
                   st.IsExecuting = false;
                   if (st.PendingReExecutionRequested)
                   {
                       st.PendingReExecutionRequested = false;
                       // キューにあった分を1回だけ再実行する
                       // （再帰呼び出しではなく、同一箇所のロジックを再度呼ぶ形にする）
                   }
               }
           }
       }
   }
   ```

3. `Program`型・`GyroCalibrate`型についても同一パターンを適用する。

4. **キュー方式の深さは1件までとする**（gwin7ok氏の「実行キューに入れて…実行される形にしたい」というご要望に沿う設計だが、無制限キューにすると、今回のバグのような「際限なく成立イベントが発生し続ける」状況で実行待ちが無限に積み上がるリスクがあるため、意図的に「直近1回分のみ覚えておく」方式に制限する）。§3の④是正（`RequiresFreshPressAfterReset`）と組み合わせることで、そもそも異常な連続成立自体が起こりにくくなるため、キューの深さ1という制限は実運用上問題にならない見込みである。

### 4.4 リスクと確認事項

| リスク | 対応 |
|---|---|
| `finally`ブロックからの再実行が、さらに`IsExecuting`のチェックと絡んで無限再帰・デッドロックを起こさないか | 再実行は「もう一度だけ」であることをコードの構造上保証する（`while`ループ等にせず、`if`一回分の再実行に限定する） |
| `Program`型・`GyroCalibrate`型など、実行内容によっては「重複してもそもそも問題にならない」ものまで一律にガードしてしまわないか | 型ごとに実際の処理内容（外部プロセス起動・ジャイロキャリブレーション等）を再確認し、真に重複実行を避けるべき型にのみ適用する |
| デバイス間で同名の`SpecialAction`が共有される場合の扱い | 本書のスコープでは対象外とし、現行の「`ActionInstanceState`はデバイスごとに独立」という既存設計を踏襲する（§4.2末尾参照） |
