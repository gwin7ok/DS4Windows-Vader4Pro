## 1. 目的

Phase6-Plan.md §0.2で暫定リスト化した193件の`Global.*`実利用箇所について、**実装前に個々の対応方針を確定**する。Phase5-Watchpoints報告書で判明した教訓（grep未確認の具体例記述が後続計画の前提を誤らせた）を踏まえ、本Stepは**一切の実装を行わず、監査と分類のみ**を行う。

Step2以降（`ControlService.cs`等の実装Step）は、本Stepの成果物である分類レポートを一次情報として着手する。

---

## 2. 監査方法

### 2.1 対象データの取得
1. `git clone --depth 1 --branch For-DI-migration-work`（または既存クローンの`git pull --ff-only`）で最新コードを取得する。
2. `DS4Windows/DS4Control/ScpUtil.cs`から`public/internal static`メンバ一覧を正規表現ベースで抽出する（Phase5-Step13+14監査で用いた手法を踏襲）。
3. 抽出した全メンバ名について、リポジトリ全体を対象に以下の2パターンで参照元を検索する。
   - 修飾形式: `Global.<メンバ名>`
   - 無修飾形式: `using static DS4Windows.Global;`を宣言しているファイル（`Mapping.cs`, `ControlService.cs`, `DS4LightBar.cs`等）内での単語境界一致

### 2.2 除外対象の確定（Phase6-Plan.md §0.3準拠）
以下は分類作業から除外し、除外理由とともに記録する。
- テストファイル（`*Tests.cs`）内の`Global.*`参照（新旧比較の意図的な参照）
- 真の定数（`const`宣言、`readonly`の不変値）
- `Mapping.cs`のうち、既存方針で「対応不要」と位置付けられている参照（`IDeviceStateAccessor`経由に既に置換済みの箇所等）
- DIサービス自身の内部実装（`ProfileRepository.cs`等）からの`Global`参照で、Strangler Fig委譲として意図的なもの

### 2.3 分類基準

各参照候補を以下の3分類のいずれかに仕分ける。

| 分類 | 定義 | 判定方法 |
|---|---|---|
| **(a) 単純リダイレクト** | 既存DIサービス（`IProfileSettingsService`, `IDeviceStateService`, `IAppSettingsService`, `IPathService`, `IEnvironmentService`, `IAppearanceSettingsService`等）に、同一のGetter/Setterまたは同等メソッドが**既に存在する** | 対象のDIサービスインターフェース（`DS4Windows/DI/*.cs`）をgrepし、同名または同義のメンバの有無を確認する |
| **(b) 中程度作業** | 既存DIサービスへの**軽微な拡張**（プロパティ・メソッドの追加）で対応可能。Phase5-Step14前クリーンアップのPR-B〜Dと同水準の作業量 | 既存サービスのクラス設計思想（薄いGlobal委譲シム）に沿って1〜数メンバ追加すれば足りるかを判定する |
| **(c) 要設計** | 対応する既存DIサービスが存在せず、新規インターフェースが必要、または既存サービスの責務境界を見直す必要がある | 全て洗い出したうえで、新設が必要な場合はインターフェース名・責務範囲の草案を添える |

### 2.4 ホットパス判定（Step2向けの追加分類）
`ControlService.cs`・`Mapping.cs`・`Mouse.cs`・`MouseCursor.cs`内の参照については、上記3分類に加えて以下を判定し記録する。
- **ホットパス該当**: 入力ポーリングループ（`On_Report`系メソッド、`MapCustom`系メソッド等）から直接・間接に呼ばれる経路にあるか
- **非ホットパス**: 起動時・設定変更時等、低頻度でのみ呼ばれる経路

## 3. 成果物

`docs-forDIMG/MadeByAgent/Phase6-Step1-Global-Usage-Classification-Report.md`として以下を含める。

1. **全件一覧表**: ファイル別・メンバ名・行番号・分類（a/b/c）・ホットパス該当有無・移行先候補サービス名
2. **除外一覧表**: 除外したメンバと除外理由
3. **サマリ集計**: ファイル別・分類別の件数集計（Phase6-Plan.md §0.2の暫定表を実測値で更新）
4. **要設計項目の詳細**: 分類(c)に該当した項目について、想定インターフェース名・責務・配置先候補を記載
5. **Step2以降への申し送り**: 各Stepの対象件数が、Phase6-Plan.md記載の暫定件数（39/12/41/22/18/39/29）からどの程度乖離したかを明記し、乖離が大きい場合はStep2以降の計画見直しの要否を記録する

## 4. 作業手順

1. `git clone`（または`pull`）でリポジトリを最新化する。
2. `ScpUtil.cs`から静的メンバ一覧をスクリプトで抽出する。
3. 各メンバについて、修飾形式・無修飾形式の両方でリポジトリ全体を検索する。
4. 除外対象（§2.2）を除いた上で、残りの参照を分類基準（§2.3）に従って仕分ける。
5. `ControlService.cs`等コア層4ファイルについては、ホットパス判定（§2.4）を追加で行う。
6. 既存DIサービスインターフェース（`DS4Windows/DI/*.cs`）と突き合わせ、分類(a)(b)の移行先候補を具体的なサービス名・メンバ名まで特定する。
7. 分類(c)に該当する項目があれば、想定インターフェース設計の草案をまとめる。
8. 成果物（§3）を作成する。

## 6. リスク

| リスク | 対応 |
|---|---|
| 正規表現ベースの静的メンバ抽出が、複数行にまたがる宣言や特殊な記法を見逃す | Phase4-Step0の「Globalメンバー442件」棚卸し結果と本Stepの抽出結果を突き合わせ、大きな差異があれば手動確認で補完する |
| `using static`による無修飾呼び出しの検出漏れ | 単語境界一致検索を`using static DS4Windows.Global;`宣言ファイルに限定して適用し、誤検出（無関係な同名ローカル変数等）を目視で除外する |
| 分類(c)（要設計）が想定より多く発生し、Phase6全体の見積りに影響する | 発生した場合はStep1完了報告時点で見積り修正案を提示し、Step2着手前にユーザーの承認を得る |
